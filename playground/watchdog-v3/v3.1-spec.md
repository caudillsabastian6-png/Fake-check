## 1. What V3.1 is

V3.1 watches **V2 only**. V2 is the host-health watchdog
(`~/bridge-watch-v2.sh`, PID 29431 at last check, 5-minute ticks,
writes `~/bridge-watch-vitals.jsonl` and to `~/bridge-watch.log`).
V3.1 does not watch V1 — that is V3's job (see `v3-spec.md`).
V3.1 does not replace V2 in this draft.

V3.1 is a **meta-watcher for host health**: it reads V2's vitals
and ticks, validates them, probes the checks V2 lacks (as audit
probes only), and reports where V2's own claims do not match its
code. Where V3 is bridge-focused, V3.1 is numbers-focused: it
cares whether V2's vitals are complete, fresh, trending, and
honest — not whether the bridge is up, which V2 was never
designed to watch (its header says so: it is NOT the old
Crostini bridge watcher, and on full Linux there is no vshd
bridge to watch).

## 2. What V2 does, and what V3.1 audits about it

| V2 check / claim (as written) | V3.1 audit of that check / claim |
|---|---|
| Vitals JSONL, one line per tick: `ts, avail_mb, load, disk_pct, tailscaled`, rotated at ~5 MB | V3.1 validates every new vitals line: all fields present, numeric where numeric, timestamp parseable, `tailscaled` in a known set. A malformed line is reported as `VITALS-MALFORMED`, not silently skipped. V3.1 also reports vitals freshness: no new line in 15 minutes while V2's process is present = `V2-STALE`; no V2 process at all = `V2-MISSING`. V3.1 does NOT restart V2. |
| Memory thresholds: ≥500 OK, 300–499 WARNING, <300 CRITICAL | V3.1 re-derives the state from the vitals history and compares it to V2's own log line for that tick. If V2 logged OK while vitals show <300 MB, V3.1 reports `V2-MISMATCH memory`. V3.1 also computes the trend V2 lacks: 3 ticks falling ≥200 MB each = `TREND-WARNING` (report only, see §3.1). |
| Load, disk % (numeric, WARNING at ≥90%, never auto-delete) | Same validation as memory: re-derive from vitals, compare to V2's log, report mismatch. V3.1 never auto-deletes. |
| Tailscaled: `systemctl is-active`, restart only if service is dead | V3.1 counts V2's restart lines in the log per hour (see §3.3). V3.1 does NOT restart tailscaled itself. If V2's log says "trying restart" but the next tick still shows tailscaled not active, V3.1 reports `V2-RESTART-INEFFECTIVE`. |
| Header claim: "watches … tunnel, cloud-serve" | **Claim-vs-code mismatch, recorded plainly (AI Loop audit §3, item 1):** V2's code watches Tailscale only; tunnel/cloud-serve are comments, OFF by default. V3.1 reports this as `V2-CLAIM-GAP tunnel, cloud-serve` on every report until the header is corrected or the checks are added. V3.1 does not edit V2's header to hide the gap — the gap is the finding. The corrected header wording V3.1 proposes (for owner approval, not applied here) is: "watches host health: memory, load, disk, Tailscale. Tunnel/cloud-serve checks are OFF by default pending a tunnel-home decision." |
| Header claim: "max 3 restarts per service per hour" | **Claim-vs-code mismatch, recorded plainly (AI Loop audit §3, item 2):** neither V1 nor V2 implements a counter. V3.1 implements the counter as an **audit counter** in this draft (see §3.3): it counts, it reports a violation, it does not gate a restart, because this draft restarts nothing. The counter code in the draft script is written so that a future owner-approved non-audit build could use the same counter to gate restarts — but that gating is NOT active in this draft, and V3.1's spec says so explicitly, so no one mistakes a report for enforcement. If the owner prefers, the alternative resolution is to remove the claim from V2's header — V3.1 lists both options, it does not pick one by editing V2. |
| No mount checks | V3.1 adds mount **audit probes** (read-only, corrected paths — see §3.2). It reports mount presence; it does not mount, remount, or fix mounts. |
| No tunnel check (OFF by default) | V3.1 adds a tunnel **audit probe** (read-only `pgrep -f cloudflared`). It reports tunnel presence; it does not run `start-tunnel.sh`. Tunnel-home gating is preserved: V3.1 reports tunnel state, it does not decide tunnel home. |
| No cloud-serve check | V3.1 adds a cloud-serve **audit probe** (read-only curl to :8080). It reports the probe result; it does not start cloud-serve. |
| No journal/vshd scan | V3.1 does NOT add a journal scan as its own focus — that is V3's bridge job. V3.1 records journal counts only if they appear in V2's vitals (they do not, in V2 as written), and reports `JOURNAL-NOT-IN-VITALS` as a known gap, not as a V3.1 feature to duplicate. Duplicating V3's journal scan inside V3.1 would blur the V3/V3.1 split the owner asked for. |
| Vitals rotation at ~5 MB; main log not rotated | V3.1 stats its own log and history (see §5) and reports V2's vitals size. V3.1 writes to its **own** log, never to `~/bridge-watch.log`, so it does not add to the V1/V2 interleaving. V3.1 does not rotate or truncate V2's files in this draft. |
| Flock single-instance guard (V2 only) | V3.1 has its own flock (see §5). V3.1 also reports a shared-writer risk it cannot fix in audit mode: V2's flock stops a second V2, it does not stop V1 writing to the same log — that is a V3 shared-log finding, cross-referenced here, not re-solved here. |

## 3. What V3.1 adds that V2 lacks

### 3.1 Vitals trend (report only)
- V3.1 keeps its own history of V2 vitals lines it has seen
  (appended, not edited, in `~/watchdog-v3-1-history.jsonl` in a
  future install; proposal only in this draft).
- Trend rule, same as V3's, as a **report state only**: 3 ticks
  falling ≥200 MB each = `TREND-WARNING`, even above 500 MB.
  This is the "spot it before it happens" signal V2's
  single-tick thresholds cannot give.
- V3.1 also reports vitals **sequence gaps**: V2 as written has
  no monotonic sequence number, so a missing tick cannot be
  distinguished from a slow tick by sequence alone. V3.1
  reports this as `VITALS-NO-SEQUENCE` and measures gaps by
  timestamp difference instead (expected 300 s ± tolerance;
  a gap >900 s with no vitals line = `VITALS-GAP`). A future
  V2 revision could add a sequence number — that is a proposal
  for V3.1's report, not an edit V3.1 makes to V2.

### 3.2 Missing-check audit probes (read-only)
- **Mounts, corrected paths:** same corrected share paths as
  V3 §3.3 (`/mnt/shared/removable/Cauldron`,
  `/mnt/shared/removable/SSD`, `/mnt/shared/removable/potions fil`,
  read-only directory presence). V3.1 reports
  `V2-MISSING-CHECK mounts` + the probe result, so a reader
  sees both that V2 does not check mounts and whether mounts
  are actually present. V3.1 never mounts.
- **Tunnel:** read-only `pgrep -f cloudflared`. Report
  `V2-MISSING-CHECK tunnel` + probe result. No start-tunnel.
- **Cloud-serve:** read-only `curl -sf http://127.0.0.1:8080/`.
  Report `V2-MISSING-CHECK cloud-serve` + probe result.
  No cloud-serve start.
- These probes are why V3.1 is not just a vitals validator:
  without them, a V2-only log looks healthy while tunnel or
  cloud-serve is dead — the exact "false-healthy log" failure
  the AI Loop audit warned about for a V2-only upgrade.

### 3.3 Restart-rate counter — implemented as audit, not as gate (this draft)
- State: V3.1 keeps a per-service, per-hour count file (in a
  future install, `~/watchdog-v3-1-restart-counts.json`; in
  this draft, the format is specified, the file is not live).
  On each tick, V3.1 scans V2's log lines since the last tick
  for restart attempts (`trying restart`, `restart tailscaled`)
  and increments the count for that service in the current
  hour window.
- Rule: count >3 in one hour for one service =
  `RESTART-RATE-VIOLATION <service> <count>/hour`, reported
  in V3.1's report. This is the enforcement of the *claim* as
  a measurement: V3.1 proves whether the claimed limit is
  being honoured, without itself restarting anything.
- Future gating (NOT in this draft, needs its own owner yes):
  the same counter, in a non-audit build, would suppress a
  fourth restart in the hour and log `RESTART-SUPPRESSED`.
  V3.1's draft script contains that gating logic only as a
  commented-out, clearly marked block, so a reader can see
  what gating would look like without V3.1 performing it.
  Until that future build is approved, the honest wording in
  every V3.1 report is: "restart limit: reported, not enforced."
- The same counter logic applies to V1's restart lines if
  V3.1's report is read alongside V3's — but V3.1 counts V2's
  lines only, to keep the V3/V3.1 split clean. Cross-counting
  is the AI Loop audit's job, not V3.1's tick job.

### 3.4 The <300 MB "pause" claim — audited, not performed
- V2's code logs "pause non-essential jobs" below 300 MB but
  pauses nothing (AI Loop audit §4, item 6). V3.1 audits this:
  when vitals show avail <300 MB, V3.1 checks whether any shed
  record exists (there is none in V2's code path) and reports
  `V2-CLAIM-UNIMPLEMENTED pause-below-300MB`.
- V3.1 drafts the real shed order as a **proposal** (crew
  browser first, then cloud-serve pause, then batch jobs,
  never tailscaled/sshd/watchdog), for owner approval in a
  future non-audit build. In this draft, V3.1 performs no shed.
  The spec states both options plainly: implement the shed
  order, or change V2's log line to warning-only. V3.1 does
  not pick one by editing V2.

### 3.5 Separate log file (V3.1's own)
- V3.1's log: `~/watchdog-v3-1.log`, rotated at 5 MB.
  V3.1's history: `~/watchdog-v3-1-history.jsonl`, rotated
  at 5 MB. Neither is `~/bridge-watch.log`.
- This separation is itself a finding about V2: V2 writes to
  the shared log, so its ticks interleave with V1's. V3.1
  demonstrates the separated pattern V2 (or its successor)
  should adopt, without changing V2's log destination in
  this draft.

## 4. What V3.1 does NOT do (this draft)

- Does NOT edit `~/bridge-watch-v2.sh` (V2) or
  `~/bridge-watch-loop.sh` (V1).
- Does NOT kill, restart, or start any watchdog, service,
  tunnel, or cloud-serve. The restart counter (§3.3) reports;
  it does not gate, in this draft.
- Does NOT auto-add tunnel/cloud-serve/mount checks to V2.
  V3.1 probes them and reports the gap; adding them to V2 is
  a NEEDS-OWNER-YES future change.
- Does NOT delete, format, dd, rotate a token, or put a secret
  in a script, vitals line, log, or report.
- Does NOT alert on routine recovery. Fix-not-alert is
  preserved: V3.1's reports are files for the AI Loop audit
  and the owner to read on a status check.
- Does NOT duplicate V3's journal/vshd scan. That split is
  intentional — see `v3-vs-v3.1.md`.
- Does NOT claim V2 is healthy because its vitals are
  well-formed. Well-formed vitals with missing checks are
  reported as well-formed *and* incomplete.

   not a restart.

   `avail_mb`, and a line with a non-numeric load. Expect
   `VITALS-MALFORMED` for each, and no crash.
3. **Claim-gap test:** mock V2 log with no tunnel/cloud-serve
   lines. Expect `V2-CLAIM-GAP tunnel, cloud-serve` in the

4. **Restart-rate test:** mock V2 log with 4 restart lines
   in one hour for tailscaled. Expect
   `RESTART-RATE-VIOLATION tailscaled 4/hour`, and no

5. **Missing-check probe test:** mock probes: mounts present,
   tunnel absent, cloud-serve present. Expect
   `V2-MISSING-CHECK` lines for all three, with probe results
   matching the mock, and no start-tunnel / cloud-serve start
   in mock output.
6. **Below-300 test:** mock vitals avail 250 MB, mock V2 log
   "pause non-essential jobs". Expect
   `V2-CLAIM-UNIMPLEMENTED pause-below-300MB` and
   `CRITICAL` state, with no shed performed.
7. **Trend + gap test:** mock vitals 1500 → 1200 → 900 MB,
   then a 1000-second gap. Expect `TREND-WARNING`, then
   `VITALS-GAP`, and `VITALS-NO-SEQUENCE` noted.
8. **Mock isolation test:** run in mock mode and confirm no
   file outside the mock output dir is written, and no
   `systemctl`, `kill`, `mount`, or restart is invoked on the
   live system.

## 7. Who watches V3.1 — the AI Loop watches the PROCESS, not just the output

**The AI Loop audit + owner review — NOT a V4.** Same
termination as V3 (see the section "AI Loop oversight of
V3/V3.1" in `v3-vs-v3.1.md`). V3.1's reports are read by
the AI Loop audit (after 20 ticks, and after any
V2-STALE / RESTART-RATE-VIOLATION / CRITICAL) and by the
owner on status checks. A V4 watching V3.1 would need a V5,
and so on — the chain stops at a periodic examiner plus a
human reader, because that is the only level that can judge
whether a report is being acted on.

Owner update, Oct 27, 00:35 ET, applied here: the AI Loop
watches over the **process** of V3.1, not just V3.1's output
lines. That means, once V3.1 is live, the AI Loop audits:
(a) this draft spec itself, against what V3.1 actually does
(spec drift); (b) V3.1's tick logs and history file, for
freshness, gaps, and states; (c) V3.1's upgrade proposals,
for whether each one is marked NEEDS-OWNER-YES and whether
any proposal would break fix-not-alert, audit-only, or the
never-delete / never-rotate-tokens rules; and (d) whether
V3.1 stayed audit-only in fact — no restart, no edit to V2
or V1, no mount, no delete, no token in any line, and no
silent activation of the commented-out restart-gating block.
A V3.1 report that looks healthy but whose process broke a
rule is a failed audit, even if every tick line says OK.

The AI Loop does NOT auto-edit V3.1, does NOT restart
V3.1, and does NOT approve its own upgrades. Owner approval
remains the final gate for every change to V3.1, and for
every upgrade V3.1 proposes to V2.
